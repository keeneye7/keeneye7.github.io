ccusage 그래프가 높으면
잘 쓰고 있는 걸까?

Spring Boot 개발 환경에서 플러그인 극단 벤치마크로 증명하는
"토큰을 많이 쓰는 게 잘 쓰는 것이다"가 틀린 이유

2026.03.27 | 12 min read | Claude Code · Max 5x · JVM
TL;DR

동일한 Spring Boot 작업을 수행할 때, 최적화된 환경은 무최적화 대비 82% 적은 토큰으로 67% 빠르게 완료한다. 토큰 소비량은 생산성 지표가 아니라 비효율의 신호다.

토큰 = 생산성이라는 착각

조직 내에서 이런 말을 들어본 적 있을 것이다. "나는 하루에 토큰을 X만큼 쓴다." 이것은 자랑이다. "이번 주 팀 토큰 사용량이 N% 증가했다." 이것은 성과 보고다. ccusage 그래프가 올라가면, 잘 활용하고 있다고 믿는다.

이것은 소프트웨어 개발에서 Lines of Code를 생산성 지표로 쓰는 것과 구조적으로 동일한 오류다. 10,000줄 코드를 작성한 개발자가 1,000줄 작성한 개발자보다 생산적인가? 당연히 아니다. 동일한 기능을 1,000줄로 구현한 쪽이 더 낫다.

동일한 결과를 적은 토큰으로 달성하는 것이 더 높은 숙련도를 나타낸다.

실험 설계

작업은 단순하다. Spring Boot 서비스에 REST API 엔드포인트 1개 추가. Controller, Service, Repository, DTO, 테스트 3개, 빌드 검증까지. 시니어 IC가 Claude Code로 30~120분에 완료하는 일반적인 업무다.

이 동일한 작업을 플러그인 설치 조합 5단계로 수행했다.

// 실험 구성 5단계 L0 Bare Claude Code만. 플러그인 없음. Opus 풀. CLAUDE.md 10K. L1 +LSP jdtls 추가. 코드를 구조로 탐색. L2 +RTK RTK 추가. CLI 출력 85~97% 압축. L3 Optimized opusplan + CLAUDE.md 3K + 스킬 on-demand. L4 Extreme L3 + /compact + 서브에이전트 + /effort 제어.

L0(무최적화)는 가장 많은 토큰을 소비하면서 가장 느렸다. L4(극한 최적화)는 가장 적은 토큰을 소비하면서 가장 빨랐다. 토큰 소비와 생산성은 양의 상관관계가 아니라 음의 상관관계에 있다.

토큰은 어디서 낭비되는가

grep은 코드를 "텍스트"로 본다. LSP는 코드를 "구조"로 본다. 하루 50회 탐색 기준으로 74만 토큰 차이. L0 사용자의 ccusage가 높은 이유는 "잘 쓰고 있어서"가 아니라 "비효율적으로 찾고 있어서"다.

Gradle의 verbose 출력에서 Claude가 판단에 사용하는 정보는 "통과/실패" 한 줄 뿐이다. 나머지 4,850 토큰은 순수 노이즈인데, 이 노이즈가 컨텍스트에 적재되어 매 턴마다 캐시 리드로 재처리된다.

Phase 3: 컨텍스트 누적 — 숨겨진 복리

이것이 가장 과소평가되는 비용이다. CLAUDE.md는 매 턴마다 캐시 리드된다.

// CLAUDE.md 10K의 40턴 세션 캐시 리드 턴 1: [10K] + [메시지 1K] = 11K 처리 턴 10: [10K] + [이전 40K] + [1K] = 51K 처리 턴 40: [10K] + [이전 150K] + [1K] = 161K 처리 CLAUDE.md 캐시 리드 총계: 10K × 40 = 400,000 tokens // CLAUDE.md 3K로 줄이면 CLAUDE.md 캐시 리드 총계: 3K × 40 = 120,000 tokens 절감: 280,000 tokens (CLAUDE.md 7K 줄인 것만으로)

관리자는 A가 "Claude Code를 잘 활용하고 있다"고 해석한다. 그래프가 높으니까. 하지만 커밋당 토큰으로 보면 이야기가 완전히 바뀐다.

총 토큰 커밋 수 토큰/커밋 판정
개발자 A 12.5M 23 543,000 비효율
개발자 B 2.3M 31 74,000 효율적

B는 A보다 커밋당 토큰이 86% 적으면서 커밋 수는 35% 많다. 모든 차원에서 B가 우월하지만, 총량 메트릭은 A가 "잘 쓰고 있다"고 말한다.

추적해야 할 메트릭

메트릭 의미 좋은 방향
❌ 총 토큰 소비 없음 (노이즈) —
✓ 토큰 / 커밋 커밋 1개의 효율 ↓ 낮을수록
✓ 턴 / 작업 왕복 횟수 ↓ 적을수록
✓ 1턴 완료율 첫 시도 성공률 ↑ 높을수록
✓ 빌드실패→수정 턴수 에러 해결 효율 ↓ 적을수록

토큰 낭비의 4가지 구조적 원인

1. 탐색 비효율 (LSP 부재) — 코드를 텍스트로 검색하면 수백 개 무관한 결과가 반환되고, Claude가 이를 추론 토큰으로 필터링한다. jdtls 설치만으로 99% 절감된다.

2. 출력 노이즈 (RTK 부재) — Gradle, Git, 스택트레이스의 verbose 출력이 컨텍스트에 적재된다. Spring의 CGLIB 프록시 스택만 50줄인데, 의미 있는 정보는 "어디서 무슨 에러" 한 줄뿐이다. RTK로 85~97% 압축된다.

3. 컨텍스트 비대 (CLAUDE.md 과적재) — "언젠가 필요할지 모르니까" 모든 규칙을 CLAUDE.md에 넣으면 매 턴 캐시 리드로 복리 누적된다. 10K→3K 압축으로 40턴 세션에서 28만 토큰 절감.

4. 재작업 (프롬프트 모호성) — "이거 만들어줘"는 clarification 왕복을 유발한다. "src/X.java:42 NPE 수정, null check 추가, Optional 반환으로 변경"은 1턴에 끝난다.

결론: 토큰 효율성 = 엔지니어링 숙련도

토큰을 많이 쓰는 것은 자랑이 아니다. 좋은 코드가 짧은 것처럼, 좋은 Claude Code 환경은 불필요한 토큰이 없다. 좋은 아키텍처에 불필요한 의존성이 없듯이.

ccusage 그래프가 높은 팀원에게 물어보라. "혹시 LSP 쓰고 있어요?" 대부분의 경우, 답은 아니오일 것이다.

5분 안에 적용하는 체크리스트
RTK 설치 — cargo install --git https://github.com/rtk-ai/rtk && rtk init -g 30초
jdtls 설치 — /plugin install jdtls@claude-code-lsps 2분
CLAUDE.md 3K 이하로 압축 — 상세 규칙은 .claude/skills/ 로 이동 10분
모델 전환 — /model opusplan 5초
습관 — 30턴마다 /compact, 작업 전환 시 /clear 매일

내일 아침 이것만 하면, ccusage에서 토큰은 줄고 커밋은 늘어날 것이다.
